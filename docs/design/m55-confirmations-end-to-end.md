# M55：Restart / Shutdown Daemon 的确认走真机流程；对话框的回车与 Esc

状态：已完成。只改了应用内自检与 E2E（产品代码没有变化）。
关联 `m53-confirm-destructive-actions.md`、`m54-real-dialog-buttons-and-quit.md`。

## 1. 背景

M54 之后还剩：Restart 与 Shutdown Daemon 的确认只有单元测试；对话框里的回车 / Esc 没有测试。后者关系到安全性——如果回车就是「移除」，确认对话框对习惯性敲回车的人形同虚设。

## 2. 做法

- **G12（failed 沙箱流程）**：Restart 改为走按钮入口——对话框出现 → 点「重建」→ 旧沙箱消失、新沙箱 running、Exec 正常。流程结尾由「Rm」改为 Shutdown Daemon：名下还有一台 running 沙箱 → 对话框出现（正文写明几台沙箱会结束）→ 点「取消」→ 对这台沙箱 Exec 仍然成功、daemon 仍 connected → 再点一次 →「关闭 daemon」→ 界面显示 daemon 已停止；脚本核对 daemon 进程确实退出、cow-root 零残留。
- **G14（确认对话框 + 假 daemon）**：读取对话框里各按钮的快捷键——「移除」没有绑定回车，「取消」绑定 Esc；实际把回车发给对话框，对话框仍在；发 Esc，对话框收起；整个过程假 daemon 只收到 `ps` / `info`。

## 3. 验证

- 全量 `e2e-all.sh`：见证据文件。

## 3.1 一次没有查清的偶发失败

本轮第一遍全量 `e2e-all.sh` 里，`m30-gui-app` 失败了一次（81 通过 / 7 失败）。随后同一份代码单独重跑 8 次、全量重跑 2 次，全部通过（87/87），没有复现。

**我没能查清原因，而且是我自己弄丢了线索**：`e2e-all.sh` 当时把失败的断言打印出来了，但我的过滤命令只留下了计数行；证据文件里也只有计数；我在看明细之前就把那份失败的证据文件删了。7 条失败 + 81 条通过 = 88 > 87，说明是某一个流程中途失败后的连带失败，但具体哪一步不知道。可能的方向（均未证实）：对话框出现的 6 秒等待在全量运行的负载下不够；有人使用的会话里窗口焦点变化影响了对话框挂载。

为此做了一处改进：`e2e-all.sh` 现在把失败套件的 FAIL / FATAL / LEAK 行逐条写进证据文件（每个套件的 `failures` 字段，harness 自检有一条用例覆盖）。下次偶发失败时，证据里就有是哪一条。

## 4. 诚实边界
- **`m30-gui-app` 有一次未查清的偶发失败**（见 §3.1）：10 次运行中 1 次。在查清之前，不能说这个套件是稳定的。

- 按键是合成的 `NSEvent`，直接交给对话框窗口（`performKeyEquivalent`，不行再 `sendEvent`），没有经过系统的事件分发；与 M31 起 ⌘Q 的测法相同。
- 「回车不执行移除」是 SwiftUI 对 destructive 角色按钮的现行行为，不是我们自己的代码保证的；这条测试的价值在于系统行为变了能发现。
- G12 的流程不再覆盖「failed 沙箱重建之后 Rm」；Rm 的真机路径在 G10。
- 菜单栏弹窗 → 主窗口弹确认这条路仍未测试；真正的鼠标事件仍未测试。
- 本轮没有做变异检查（产品代码未变；M54 已验证点击确实经过视图里的按钮）。
